# MathCrossword v20 — юбилейный baseline

## Зачем этот релиз

v19 исправил содержание hard Path: уровни 70+ перестали тихо падать в Logic 3, появился replay и математически правдоподобные ложные кандидаты. Но профилирование показало вторую проблему: некоторые уровни могли собираться 6–10 секунд, потому что дорогая работа повторялась на кандидатах, которые затем всё равно отбрасывались.

v20 не ослабляет hard gate ради скорости. Он меняет **порядок и стоимость поиска**.

## Что показал профайлер

На медленных v19 seed большая часть времени уходила внутрь hidden-mask search:

- `TILE_POOL`;
- exact uniqueness;
- `HumanSolver`;
- повторный `CascadeResilienceAnalyzer`;
- после этого ещё строились deceptive-decoys, даже если сама базовая задача не проходила Path acceptance.

То есть генератор слишком долго доказывал качество слабых кандидатов.

## v20: отдельный Path search intent

`GameConfig.pathMode` используется только для hard Path. В этом режиме:

1. hidden search тратит меньший bounded budget на одну геометрию;
2. промежуточные маски оцениваются HumanSolver-метриками устойчивости к каскаду;
3. подробный truth-reveal/cascade profile не пересчитывается для каждого промежуточного mask;
4. сохраняются только маски, уже попавшие в нужный Logic band и Path anti-collapse gate;
5. outer search быстрее переключается на другую геометрию, если текущая форма не даёт нужной задачи.

Это переносит бюджет от «долго улучшать слабую форму» к «быстрее искать другую подходящую форму».

## TileBankBuilder: support provenance

До v20 equation-derived ложное значение попадало в общий pool, после чего проверялось против **каждой** hidden-клетки. Но сам этап алгебраического вывода уже знает, для каких клеток значение имеет смысл.

v20 сохраняет эту связь `value -> hinted positions` и запускает дорогую локальную проверку только там. Для secondary neighbourhood values общий fallback остаётся. Это не меняет математический safety gate, но убирает много повторной работы.

## DeceptiveDecoyBuilder: expensive validation after ranking

Раньше bounded lookahead запускался почти для каждого правдоподобного `(cell, value)` кандидата. Теперь:

1. сначала строятся локально допустимые supports;
2. values ранжируются по support count / crossing weight / близости к truth;
3. bounded lookahead получает только верхний ограниченный frontier;
4. exact uniqueness по-прежнему остаётся последним обязательным gate.

## Decoy rollback

В v19 нашёлся важный эффект: хороший Logic-4 puzzle мог пройти Path gate, после чего дополнительный believable decoy расширял candidate space так, что HumanSolver видел уже более длинный forced cascade. Формально decoy был ложным и unique-safe, но **ухудшал форму задачи**.

В v20 decoys добавляются по одному. После добавления проверяются те же Path difficulty/cascade gates. Если tile ухудшает структуру, он откатывается, а уже хорошая задача не выбрасывается. Поэтому количество deceptive-decoys на конкретном уровне может быть 0, 1 или 2/3 — качество важнее квоты.

## Контрольный benchmark

Сравнение использует один и тот же набор уровней `70,75,80,85,90,95,100` и существующий v19 reference CSV. Wall time зависит от JVM/машины, поэтому это инженерный regression benchmark, а не универсальная производительность устройства.

| Level | v19 ms | v20 ms |
|---:|---:|---:|
| 70 | 2006 | 1439 |
| 75 | 2096 | 549 |
| 80 | 573 | 450 |
| 85 | 6433 | 1651 |
| 90 | 1868 | 1675 |
| 95 | 9552 | 746 |
| 100 | 7510 | 194 |

Среднее на этой небольшой контрольной выборке: примерно **4291 ms -> 958 ms**, то есть около **4.5× быстрее**. Самые большие выигрыши пришли не от «быстрого solver», а от того, что слабые кандидаты перестали получать дорогую обработку.

Контрольный v20 CSV: `tools/benchmark_notes_v20_path_70_100.csv`.

## Что не изменилось

- exact unique solution остаётся обязательным;
- уровни 70+ остаются hard Path / Logic 4;
- replay/test semantics v19 сохранены;
- deceptive values не могут совпадать с hidden truth;
- generic Path остаётся ортогональным;
- HumanSolver остаётся моделью игровых стратегий, а не моделью психологии человека.

## Следующий фронт

После v20 основной остаточный расход — не один универсальный bottleneck. На некоторых seed это hidden uniqueness/HumanSolver, на других — построение качественных deceptive candidates. Следующий шаг лучше делать по накопленной `generationStageTimings` статистике реальных Path-сессий, а не увеличивать общий retry budget.
