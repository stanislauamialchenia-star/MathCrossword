# MathCrossword — технический аудит после v9

## Состояние проекта

MathCrossword уже не является одним Canvas-прототипом. В проекте есть процедурный генератор, точный solver, human-like solver, анализатор логической структуры, стратегии решения, локальный play trace и библиотека способов решения.

Главная ценность проекта сейчас — не UI, а связка:

`генерация -> проверка единственности -> оценка структуры -> человеческая модель решения -> реальное прохождение`

## Что исправлено по сравнению с God Object

В ранних версиях почти всё находилось в `MainActivity.java` (около 130+ КБ). В v8 основной генератор и анализ уже вынесены. `MainActivity.java` теперь примерно 59 КБ и в основном отвечает за Android UI/состояние экрана.

Android-независимое ядро:

- `PuzzleModel`
- `GameConfig`
- `PuzzleGenerator`
- `GeneratorPolicy`
- `SolutionCounter`
- `HumanSolver`
- `LogicAnalyzer`
- `HintEngine`
- `SolutionStrategy`

Android-зависимый слой:

- `MainActivity` — Canvas, touch/UI/lifecycle;
- `SessionTracker` — Context, SystemClock, внутреннее хранилище.

Это важнее немедленного перехода на Kotlin/MVVM/Compose: теперь генератор можно запускать как обычную JVM-программу.

## Почему генератор не должен «видеть Android»

Если генератор начинает зависеть от `Context`, `Activity`, `View`, Android storage или lifecycle, возникают лишние связи:

1. его труднее запускать без эмулятора;
2. batch-тесты на тысячах задач становятся медленнее и сложнее;
3. воспроизводимость seed смешивается с состоянием UI/lifecycle;
4. сложнее профилировать CPU/память отдельно от Android;
5. сложнее позже использовать тот же engine в desktop/server/test tooling;
6. машинное обучение или внешний ранжировщик придётся связывать с Android вместо чистой модели данных.

Правильная граница: Android просит ядро «создай Puzzle», а ядро возвращает обычные Java-объекты и ничего не знает о телефоне.

## Полигон генератора

`tools/GeneratorHarness.java` запускает генератор без Android и выводит метрики по стратегиям/Logic. Это уже позволяет искать слабые места не вручную на телефоне, а сериями.

Текущий следующий шаг для полигона:

- property tests;
- распределения по 1000+ seed;
- latency percentiles (p50/p95/p99), а не только среднее;
- доля отказов генерации по стратегии;
- fingerprint геометрии и повторяемость;
- сравнение predicted difficulty с фактическим play trace.

## Наводящие подсказки

v8 добавляет Android-независимый `HintEngine`.

Ключевой принцип: подсказка должна прежде всего менять **направление внимания**, а не выдавать ответ.

Уровни помощи:

1. область/стратегия;
2. кандидаты/сужение;
3. конкретный логический тест или, в forced-случае, единственный кандидат.

Подсказки логируются, поэтому позже можно измерять не только время решения, но и место, где модели игрока не хватило собственного инструмента.

## Что пока НЕ стоит делать

- полный rewrite на Kotlin;
- обязательный Compose для игрового Canvas;
- Firebase/сетевую аналитику;
- Room только ради нескольких настроек;
- ML вместо точного solver;
- новые операции без улучшения генератора.

## Следующий технический приоритет

1. Увеличить автоматическое покрытие генератора.
2. Собирать реальные traces и сравнивать их с HumanSolver.
3. Калибровать `GeneratorPolicy` по расхождениям.
4. Добавить модель «следующего полезного задания» без ML — обычной статистикой/правилами.
5. Только после накопления данных оценивать, где ML действительно превосходит прозрачные эвристики.


## v9 — временный слой устойчивости

Chain/Network пока хуже попадают в строгий целевой профиль, чем Hypothesis/Mixed. Вместо большого скрытого числа повторов v9 использует маленький строгий бюджет и provenance-marked fallback. Это сознательный костыль: он сохраняет игровой поток, но статистика позволяет увидеть частоту fallback и не считать такие сессии чистыми образцами стратегии. Следующая инженерная цель — уменьшать эту частоту конструктивным генератором, а не увеличением retry budget.
